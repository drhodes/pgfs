is it possible to connect to postgres over a faster channel than tcp/ip ?
Examined alternative Postgres connection methods beyond standard TCP/IP

Yes — a few options, roughly in order of how much speedup you can expect:

Unix domain sockets (biggest easy win, same-host only)

If your client and Postgres server are on the same machine, use a Unix socket instead of TCP:

psql "host=/var/run/postgresql dbname=mydb"

or in a connection string: postgresql:///mydb?host=/var/run/postgresql

This skips the TCP/IP stack entirely (no packet framing, checksums, loopback network layer) and goes through the kernel's local socket mechanism instead. It's usually 20-40% faster for small queries and much better for latency-sensitive workloads with lots of round trips. This is the standard "faster than TCP" option and it's built into libpq — most Postgres installs listen on a Unix socket by default alongside TCP.

Shared memory / co-located approaches

If you truly need to eliminate IPC overhead (e.g., extremely high-frequency small queries), your realistic options are:

    Run your application as a Postgres extension or use PL/Python/PL/pgSQL to execute logic inside the backend process itself — no IPC at all.
    Use dblink or postgres_fdw if you're bridging between two Postgres instances, though these still go over a socket internally.
    There's no officially supported shared-memory client protocol for arbitrary client apps — Postgres's wire protocol assumes a socket (TCP or Unix) between client and backend.

Connection pooling (helps a different bottleneck)

If your bottleneck is actually connection setup/teardown rather than per-query transport, tools like PgBouncer or Postgres's own connection pooling reduce overhead by reusing backend processes, which matters a lot more than transport choice in most real workloads.

What actually matters most in practice

    Same-host: Unix socket is the correct answer and trivial to set up.
    Cross-host: TCP/IP (with reasonable tuning) is realistically your only option — there's no alternate transport in standard Postgres. RDMA-based or shared-memory cluster setups exist but they're niche, require special builds/extensions, and are not something you'd reach for outside of specialized high-performance clusters.
    If latency matters more than raw throughput, batching queries, using prepared statements, and enabling pipelining (libpq's async/pipeline mode) will usually beat any transport-level tweak.

I want to use postgres as a backend to fuse
Deciphered PostgreSQL-FUSE integration for database-backed filesystem

That's a neat project — you're essentially building a FUSE filesystem where directory entries, metadata, and/or file contents live in Postgres tables instead of on disk. This connects to your earlier question nicely: since FUSE mounts are inherently local (the kernel talks to your userspace daemon via /dev/fuse), your daemon should talk to Postgres over a Unix socket for the same-host low-latency win, since every filesystem syscall (stat, read, readdir, etc.) may turn into a DB query.

A few design considerations for this kind of project:

Schema design

    A common approach: an inodes table (inode number, type, size, mode, uid/gid, timestamps) and a dentries/links table (parent inode, name, child inode) to represent the directory tree.
    File content either goes in a bytea column (fine for small files), in Large Objects (lo_import/pg_largeobject, better for streaming/random access), or chunked into a blocks table (inode, block_number, data) if you want efficient partial writes/reads without rewriting whole blobs.

Performance is the real challenge

    Every getattr, read, write, readdir becomes a round-trip. This is where connection choice (Unix socket) and query efficiency matter most.
    Use a long-lived connection (or a small pool via PgBouncer in session mode) rather than reconnecting per syscall — reconnect overhead will dominate otherwise.
    Enable libpq pipelining or batch multiple metadata lookups when the FUSE library gives you the chance (e.g. readdir fetching many entries at once).
    Cache aggressively in your FUSE daemon (inode attribute cache, directory listing cache) with a short TTL — FUSE's own kernel-side caching (attr_timeout, entry_timeout in fuse_conn_info) also helps a lot and avoids re-querying Postgres for every syscall.
    For write, consider buffering in memory and flushing to Postgres on flush/release rather than a query per write() call, since writes can be small and frequent.

Language/binding choice

    C/C++ with libfuse + libpq gives you the most control and lowest overhead.
    Python with fusepy/pyfuse3 + psycopg is much faster to prototype but adds per-call overhead — fine for learning or low-throughput use, not great for anything performance-sensitive.
    Go with bazil.org/fuse or hanwen/go-fuse + pgx is a nice middle ground: reasonably fast, much easier to write than C.

Prior art worth looking at
There have been a few "Postgres-as-filesystem" projects over the years (pgfs-style experiments); they're mostly proofs of concept rather than production-ready, since a real filesystem workload (especially metadata-heavy operations like readdir on large directories) stresses relational queries in ways Postgres isn't optimized for compared to a purpose-built filesystem or KV store.

What's the actual goal — is this for learning/experimentation, or do you need this in production for something like exposing DB-stored files to legacy tools that expect a filesystem interface? That'll change some of the tradeoffs (e.g. whether large object streaming or block-chunking is worth the complexity).
